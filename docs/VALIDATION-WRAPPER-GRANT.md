# Exact software diagnostic manifest and admission proposal

Source: tests/support/dl2/docker_validation_software.py. This is an operator-owned
software-test proposal, not general model/candidate registration. Its four fixed
inputs are valid stdio, invalid syntax, denied os import and a marker/infinite-loop
body that must never run. Host code only packages bytes/base64/UTF-8/hashes/JSON.

build_manifest(candidate_commit) returns schema bbr.dl2.validation-manifest.v2.
It pins the exact candidate commit; validator, proposed guard/registrar, existing
worker guard and transport source paths/hashes; original candidate and wrapper
bytes as base64; candidate/wrapper/binding/import-policy hashes; full policy and
limits; actual existing image and Python-runtime-only manifest; expected software
diagnostics and their bounded rationale. check_manifest compares byte-canonical
data with reconstruction from the four fixed source literals and current source
hashes. It never parses, compiles or executes candidate text.

The new ExactValidationAdmission composes existing SoftwareGrant ownership,
mutex, empty-client-config, live daemon/image/ledger/HostConfig and RAM checks. It
does not alter docker_software_worker.SCRIPTS or that guard's five-script policy.
Only this separate guard can consider the four diagnostic wrappers, and only
with an explicit externally pinned authorization. Missing authorization causes
register/proof refusal before artifact writes, mutex/ports/Docker operations.

Constructor inputs are proposal_path/proposal_sha256 and keyword output/python,
authorization_path/authorization_sha256. The interpreter must be the approved
app-local .venv-round2 Python. Output stays under phase receipts. Both expected
file hashes must come from INT's actual messages, never from an untrusted request
or from treating a self-hashed file as authority. No permissive registrar or
default approval is supplied. These bindings do not cryptographically identify
Roy, an independent custodian or a real operator.

INT's future machine-readable authorization must have exactly:
- schema: bbr.dl2.validation-admission.v1
- decision: approved
- extension_id: a real bounded identifier without placeholder/pending/todo
- base_grant_id: M15-R2-PYTHON-SOFTWARE-20261027
- proposal_sha256: the exact new v2 file-byte hash
- guard_registrar_sha256: the source hash pinned in that proposal
- image_sha256, runtime_manifest_sha256: the already approved exact values
- project/instance/container_name/owner_id: m15/r2-candidate/m15-r2-candidate-worker/0928
- wrapper_sha256: sorted list of exactly the four proposal wrapper hashes
- limits: exact ExecutionLimits JSON (wall2s/CPU1s/streams4KiB/memory256MiB/PID1)

No example approved record is generated by this package. The operational token
<PLACEHOLDER_VALIDATION_WRAPPER_GRANT> remains until INT supplies a concrete record
and its external SHA256. Acknowledging an API or returning a readonly receipt is
not that approval.

After authorization, an operator must acquire admission.base.lease() and release
it in finally. registrar is admission.register; DockerBackendConfig uses the
same granted image/runtime, owner/lease/name/paths and admission_guard=admission.
The registrar verifies the external authorization and exact immutable wrapper
registration before exclusive digest-addressed creation, refuses mismatching
existing bytes, marks only newly authored wrapper files readonly and verifies
actual flags/hashes before returning a receipt. It approves no candidate strings
or arbitrary artifacts. No file or volume cleanup is performed.

Before each create/start, the guard rechecks the authorization/proposal/source
pins, actual readonly registered artifact, actual runtime manifest/engine/image,
current ledger/name ownership, exact container configuration and fresh RAM above
3GiB. The existing transport still performs canonical agent-ports checks and its
fresh proof/RAM refresh. Existing HostConfig checks retain readonly root, exact
16MiB /tmp tmpfs, no network/ports, UID/GID65534, caps dropped, PID1, CPU1 and
memory/swap256MiB. Cleanup belongs only to the original verified-created-ID path.

Only the trusted wrapper may execute inside the candidate container. It parses
and compiles syntax there and discards the candidate code object. The four
software expectations are test data, not independently authored corpus answers.
No real diagnostics, new containers, independent admission or live permissions
follow from producing this source/manifest. Focused fake/missing-grant units do
not establish live authorization or sandbox correctness.
